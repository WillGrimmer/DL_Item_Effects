# DL_Decision_Analytics: review and rebuild recommendation

Reviewed 2026-10-13 against `main` @ `9bfe6e2` (last commit 2026-07-24). Read-only review. Nothing was edited or pushed.

## Bottom line

**Rebuild it in a new repo. Carry over the plumbing. Redesign the counterfactual.**

The infrastructure is solid: bulk extraction, the item decoder, a correctly written cross-fitted AIPW, BH-FDR, and the page renderer. The problem is the **decision frame**, meaning how the treated and control groups are defined. It has a structural flaw that pulls every effect toward zero, or below it, outside an item's earliest buy window (shown below). It also has never had a test. On top of that, the project's current state is mostly stale (37 of 38 heroes, 4 of 5 published pages). Its 760-line PLAN.md is a log of six estimand rewrites in three days, not a design you can build on. Patching it in place would mean rewriting the core anyway while carrying all that baggage.

## Where it stands

- **Built in 3 days (Jul 22 to 24), 13 commits, about 4.4k lines.** All 50 tests pass (I re-ran them here). Every test is offline and synthetic.
- **The "improved WPA" is no longer WPA-based.** The calibrated win-prob model (`model/train.py`, AUC 0.73 to 0.76) was built, found to ignore items, and shelved. What runs today is a separate causal estimator: AIPW of "buy X in window vs. buy a same-cost item in window", using match win as the outcome.
- **There are no custom weights in the code.** The only weights anywhere are inverse-propensity weights that are *learned* inside AIPW (`estimator.py:235-262`). `grep -i weight` finds nothing else. If you remember hand-tuned weights, they live in a different project.
- **Current output is stale except for Mirage.** `roster_effects_v2.parquet`, 37 hero effect tables, and the Billy/Wraith/Abrams/Lash pages were built on a superseded estimand (10m floor, nondeterministic sampling). `hero_infernus.html` predates the cost-confound fix and is actively misleading. The README still says "Phase 0 complete".
- **The data can't be reproduced from the repo.** The corpus is one git-ignored local parquet (shard 94, roughly one week in July, Unranked queue). It has no patch or date column.

## What's wrong, ranked by how much it matters

### 1. The control arm includes players who already own the item (critical)
`decision_frame` (`estimator.py:490-523`) defines the control group as anyone who bought a same-cost item in the window **and didn't buy X in that window**. `bought_treat` is computed only over rows inside the window. So:
- Players who bought X **before** the window count as controls. They own X and they win more, so X's effect gets pulled toward zero or negative.
- Players who buy X **after** the window also count as controls. The contrast is really "X now vs. X later or never", which mixes timing with choice.
- No covariate records what a player already owns. `n_prior_items` is only a count, and sold items are ignored (`sold_time_s` is never extracted).

**Synthetic check** (`control_arm_sim.py`, which uses the repo's own `crossfit_aipw`). The true effect of owning X is +3.0pp, 65% of players buy it early, and the late window is evaluated:

| control definition | AIPW | 95% CI |
|---|---|---|
| repo's (includes early owners) | **+0.97pp** | [-0.44, +2.38] (looks "not significant") |
| risk set (hasn't bought X yet) | **+3.29pp** | [+1.71, +4.88] (recovers truth) |

The repo hides a real +3pp effect as noise. Add the fact that late buyers are behind, and the result turns negative. That is very likely part of the Mirage / Mystic Regeneration "−14.7% at 16m" result. The fix in July (lowering the time floor) hid the symptom without fixing the cause. Every item's curve after its main buy window carries this bias. That includes the "ideal timing" and "Shop at…" tabs.

### 2. Confounding control is thin
The covariates are team-average badge (not individual, and no **enemy** badge or badge gap), net worth from a snapshot up to 3 minutes stale, team net-worth diff, item count, time, and hero comp. Missing: current inventory, level, K/D/A, objectives, and **enemy builds**. Enemy builds matter a lot, because defensive and counter items are bought in response to them, and they also predict losing. The docs admit "significant ≠ causal". With this covariate set, that caveat carries most of the weight.

### 3. Uneven weighting between arms
Treated players keep one row each (their first X buy). Control players keep **every** same-cost purchase in the window (`dedup_control=False`). Richer players who buy several items in a window count multiple times as controls, so the estimand is per-purchase on one side and per-player on the other. This is a plausible contributor to the unexplained +0.5 to 0.8pp positive skew. The skew was attributed to thresholds, that idea was disproven, and then the skew was declared "benign".

### 4. The validation can't detect confounding
- **Placebo test:** it shuffles the treatment label, which only proves the code doesn't invent effects from noise. Confounding passes it untouched.
- **Synthetic unit tests:** they use a data-generating process where the assumptions hold by construction. The SQL that builds the arms, where all four July biases lived, has **zero tests**.
- **Covariate ladder:** a stability heuristic, not identification.
- **External evidence:** one Statlocker number (Lash/Refresher).
- **Not started:** no replication on a second week, no patch diff-in-diff, no negative-control outcome.

### 5. Researcher degrees of freedom
The estimand was changed six or more times, and each change was accepted when the output "looked right": the mean moved toward 0, cost correlation moved toward 0, or the result matched a prior about Mystic Regen. PLAN.md principle #1 says "Items DO matter. Any ~0 result is a MEASUREMENT ERROR", which makes the method unfalsifiable. Headline claims also drift: the plan still says "4-5% effects", while the current numbers are about 1%.

### 6. Smaller statistical issues
- **"Ideal timing" has winner's-curse bias.** It takes the max over about 16 noisy, overlapping points, so it is biased upward, and the "gap" metric inherits that bias.
- **Page significance isn't FDR-corrected.** Only the roster sweep uses BH, and its windows differ from the page windows.
- **Propensities are clipped, not trimmed** (`np.clip` at 0.02). With weak overlap, this biases AIPW instead of dropping unsupported rows.
- **Shop-at-minute ranks items that each have a different control field.** Comparing A's effect to B's is not a real A-vs-B contrast.
- **Only one week of data, Unranked queue, no patch ID.** Phase 11, the strongest identification strategy, is blocked on this.

## What to keep (port into the new repo)
- `ingest/extract.py`: the DuckDB-over-S3 pattern and ASOF joins. Add `sold_time_s`, inventory, enemy badge, level/K/D/A, objectives, and patch/date.
- `assets/decoder.py` and its tests.
- `crossfit_aipw`: correct as written (group K-fold, clustered SE). Switch from clipping to trimming.
- `benjamini_hochberg` / `add_significance`, and the overlap gates (`trim_share`, `treated_frac`).
- The hero page template and renderer.
- The lessons in PLAN.md §6, condensed to about one page.

Drop: `model/train.py` and `benchmark.py`, the `billy_*` scripts, and all cached tables and pages.

## Proposed v2 design (target-trial emulation)
1. **Decision point = each shop purchase.** A player is at risk for X only if they don't currently own X and they buy something at X's cost. Treated = buys X; control = buys another on-support item at the same cost. One row per decision.
2. **Covariates = full state at the decision:** an owned-items multi-hot, own and enemy badge plus the gap, interpolated net worth, level, K/D/A, objectives, enemy inventories by slot, and comp.
3. **Multi-valued treatment.** At each (hero, cost bucket, time) estimate effects for all candidate items against **one shared baseline** using generalized-propensity AIPW, so the shop rankings are actual pairwise comparisons.
4. **Falsification built in from day one:**
   - Negative-control outcomes. The "effect" of buying X at t on things that happened *before* t (prior 3-min kills or net-worth gain) must be ~0.
   - Week-to-week replication.
   - Patch buff/nerf diff-in-diff once a patch ID is in the data.
5. **Pre-registered acceptance criteria**, fixed before looking at hero results. Never "items must matter".
6. **A Statlocker-style WPA baseline in the same repo**, so "improves on WPA" becomes a measured claim.
7. **SQL tests** on small hand-built match fixtures. The arm-construction logic is where every past bug lived.

## Caveats on this review
I couldn't re-run anything on real match data, because the environment's network policy blocks `s3-cache.deadlock-api.com` and `api.deadlock-api.com`. Findings come from reading the code, the repo's own logged numbers, the unit tests, and the synthetic check above. How much finding #1 moves each real effect is an estimate. Its direction is not.
